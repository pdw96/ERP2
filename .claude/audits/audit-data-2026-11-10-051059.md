## 부적합 목록

### NC-18 · 잠금 설명이 `ACCESS EXCLUSIVE` 를 빠뜨린다 — 규칙 줄의 「유일 제약은 읽기가 된다」, PR B 의 「창고는 쓰기만 멈춘다」
- 위치:
  - `docs/schema.md:136-137`
  - `docs/slices/3-재고수불/design.md:260-261`(PR B 잠금). 0009 를 더한 `design.md:286-289` 에는 잠금 설명이 없습니다.
  - 실제 DDL: `drizzle/0007_number_rules.sql:42` · `drizzle/0009_default_warehouse_not_defect.sql:12-13`
- 증상:
  - (a) 규칙 줄은 「인덱스 · 유일 제약을 더할 때 — `CONCURRENTLY` 없는 인덱스는 만드는 동안 쓰기를 멈춘다(읽기는 된다)」입니다. 이 말은 `index()` · `uniqueIndex()` 가 만드는 `CREATE [UNIQUE] INDEX`(SHARE)에만 맞습니다. drizzle 의 `unique()` 는 `ALTER TABLE … ADD CONSTRAINT … UNIQUE` 를 내고, 이 형태는 `ACCESS EXCLUSIVE` 라 읽기도 멈춥니다. 이 조각의 0009:13 이 바로 그 형태입니다.
  - (b) PR B 설명은 「참조가 가리키는 `warehouses` 의 쓰기를 멈춘다」입니다. 그러나 같은 빌드의 0007:42 `ALTER TABLE "warehouses" ADD COLUMN "is_defect"` 가 `ACCESS EXCLUSIVE` 를 잡습니다. 그래서 마이그레이션이 다 끝날 때까지 창고 읽기도 멈춥니다. 리뷰에서 더한 0009 도 `warehouses`(UNIQUE) · `items`(ADD COLUMN)의 읽기 · 쓰기를 멈추는데, 설계에 잠금 줄이 없습니다.
- 근거:
  - PostgreSQL 의 `ALTER TABLE` 은 따로 적힌 것 말고는 `ACCESS EXCLUSIVE` 입니다. 따로 적힌 것은 FK 더하기(`SHARE ROW EXCLUSIVE`) · `VALIDATE`(`SHARE UPDATE EXCLUSIVE`) 따위입니다. `ADD COLUMN` · `ADD CONSTRAINT UNIQUE` 는 거기에 들지 않습니다.
  - 마이그레이션이 트랜잭션 하나라, 그 잠금은 그 빌드의 마이그레이션이 다 끝날 때까지 갑니다.
  - 배포하는 사람과 다음 저자는 이 줄을 점검표로 읽습니다. 이미 행이 있는 표에 `unique()` 를 더하면서 「읽기는 된다」고 PR 본문에 적게 됩니다.
  - 기원을 밝혀 둡니다. (a) 는 회차 22 OB-10 (b) 의 제 문구가 `CREATE INDEX` 와 「유일 제약 추가」를 한데 묶어 「SHARE 라 읽기는 막지 않는다」고 쓴 것을 줄이 그대로 옮긴 것입니다.
- 되돌림: 가능 — 문서만 고칩니다. 이미 적용된 마이그레이션은 바꿀 것이 없습니다.
- 심각도: 낮음 — 결과는 같고 문서만 어긋납니다. 전제는 셋입니다.
  - 0007 · 0009 는 상한이 있는 표(창고 99 · 품목 2,000)만 잠가 멈춤이 짧았습니다.
  - 이미 운영에 적용됐습니다. 이 전제는 레포만으로 확인할 수 없습니다 — 메인 세션이 Neon 운영 `main` 분기에서 `drizzle.__drizzle_migrations` 가 13행인지 보면 됩니다.
  - 이미 행이 있는 표에 `unique()` 를 더하는 마이그레이션이 계획되지 않았습니다. 계획되면 **보통**입니다.
- 제안:
  - (1) `schema.md:136` 을 갈라 씁니다 — 「`index()` · `uniqueIndex()` 는 `CREATE INDEX` 라 쓰기만 멈춘다(읽기는 된다). `unique()` 는 `ALTER TABLE … ADD CONSTRAINT … UNIQUE` 라 읽기 · 쓰기를 다 멈춘다. 이미 행이 있는 표에 꼭 유일을 더해야 하면 `uniqueIndex()` 로 쓰거나, 다 멈추는 것을 PR 본문에 적고 받아들인다」.
  - (2) 설계에 날짜 붙인 줄을 하나 더합니다 — 「PR B 의 0007 은 `warehouses` 에 칸을 더해 읽기도 멈췄고, 0009 는 `warehouses`(유일) · `items`(칸)의 읽기 · 쓰기를 멈췄다(상한 있는 표라 짧았다)」.
  - (3) 메인 세션이 `gh` 로 PR #27(B) · #29(C) · #35(E) 본문의 「잠그는 테이블」을 봅니다. 셋 가운데 틀린 것이 있으면 (2) 줄에 함께 적습니다. 0011 은 `items` · `warehouses` · `codes`, 0012 는 `items` · `warehouses` · `stock_moves` 의 쓰기를 커밋까지 멈춥니다.
  - 고치지는 않습니다.

- 위치: `docs/schema.md:56` — 「전표 · 줄 · 품목 · 창고는 지울 수 없다(참조)」. 대조한 곳은 `schema.ts:426-468` 과 0011 · 0012 의 FK 전부입니다.
- 증상: `stock_move_lines` 를 가리키는 FK 가 하나도 없습니다. `stock_counts.baseline_line_id` 는 참조가 아닌 정수입니다. 그래서 DB 는 줄의 `DELETE` · `UPDATE` 를 막지 않습니다. 전표도 줄이 남아 있는 동안만 참조가 막습니다. 줄을 고치거나 지우지 않는 것은 앱 쪽 보장입니다 — 코드에 그런 길이 없고(grep), ADR 0018 의 「지우거나 고치지 않는다」가 정책입니다.
- 근거: 이 절은 「화면 · 서버의 검사를 건너뛴 값도 DB 의 제약이 거절한다」는 목록입니다(`:27`). 다음 조각의 저자가 이 줄을 믿으면, DB 가 장부 줄을 지켜 준다고 보고 정리 스크립트나 손 SQL 을 씁니다. 그러면 잔액 = 줄의 합이 깨진 채 남습니다.
- 되돌림: 가능
- 심각도: 낮음 — 지금은 줄을 지우거나 고치는 길이 코드에 없어 결과가 같습니다. 문서만 어긋납니다.
- 제안: 둘 가운데 하나입니다.
  - (a) `:56` 을 「전표 · 품목 · 창고는 지울 수 없다(참조)」로 고치고, `:62-76` 「DB 가 막지 않고 서버가 막는 것」에 「수불 줄 · 잔액을 고치거나 지우지 않음 — 쓰는 곳은 `src/db/stock.ts` 하나」를 더합니다.
  - (b) DB 가 정말 막게 합니다 — `stock_move_lines` 에 `UPDATE` · `DELETE` 를 거절하는 트리거. 되돌림은 `TRUNCATE` 라 걸리지 않습니다.
  - 업무에 영향이 없는 기술 결정이라 Claude 가 정할 수 있습니다. 고치지는 않습니다.

## 관찰

### OB-12 · 수불 저장은 응답을 잃은 뒤 다시 보내면 전표가 두 장이 된다 — 재고가 그날 밤까지 두 배로 남는다
- 위치: `src/db/stock.ts:523-565`, `src/app/inventory/moves/actions.ts:28-40`
- 무엇:
  - 수불 저장에는 멱등 키가 없습니다. 같은 내용을 막는 유일 제약도 없습니다. 이것은 일부러 그런 것으로 보입니다 — 같은 품목 · 수량의 입고가 하루에 두 번 있을 수 있습니다.
  - 저장 중 단추가 꺼져 두 번 누르기는 막힙니다. 그러나 서버가 커밋한 뒤 응답이 끊기면 화면은 입력을 비우지 않습니다. 사용자가 다시 「저장」하면 같은 줄로 새 전표가 붙습니다.
  - 취소 · 새 실사 · 확정은 다시 보내도 거절됩니다(항목 6). 남은 길은 이것 하나입니다.
- 왜 부적합이 아닌가: 요구사항 · 설계 ② · ADR 0015 · 0018 어디에도 「같은 저장을 다시 보내도 한 장」이 없습니다. ② 의 「동시에 저장해도 같은 재고를 두 번 쓰지 않는다」는 서로 다른 저장의 경합을 말합니다.
- 알아 둘 값:
  - 기준정보의 같은 길(회차 13 OB-2)은 품목이 하나 더 생기는 정도였습니다. 여기서는 **잔액이 조용히 틀린 값**이 됩니다. 뒤 조각(구매입고 · 생산실적)이 이 저장을 부르면 같은 길을 물려받습니다.
  - 막으려면 화면이 연 때 토큰 하나를 숨은 칸으로 보내고, `stock_moves` 에 그 토큰의 유일 칸을 둡니다.
  - 장부에 무엇이 남는가를 정하는 일이라 저자의 판정입니다(`CLAUDE.md`).
  - 같은 꼴의 관찰은 두 번째입니다. 세 번째가 오면 「재시도의 멱등」을 규칙으로 세우자고 제안하겠습니다.

### OB-13 · 수불 줄의 자동 증가 번호가 실사 화면의 숨은 칸으로 나간다
- 위치: `src/app/inventory/counts/count-form.tsx:104`, `src/db/stock-counts.ts:236,382`
- 무엇:
  - 새 실사 화면이 장부를 읽을 때의 `max(stock_move_lines.id)` 를 `baseline` 숨은 칸으로 들고 있다가 처음 저장할 때 보냅니다.
  - 회차 13 은 「`id` 는 서버 밖으로 나가지 않는다」로 적합을 줬습니다. 이번이 그 밖의 첫 자리입니다.
- 왜 부적합이 아닌가:
  - 서버가 지금보다 큰 값을 지금으로 줄이므로(`:382`) 경고를 숨기지 못합니다. 작은 값을 꾸며도 경고가 늘 뿐입니다.
  - 드러나는 것은 지금까지의 수불 줄 수입니다. 데모는 수불 이력을 누구에게나 보이므로 새는 것이 없습니다.
  - 되돌림이 `restart identity` 로 번호를 1 부터 다시 세도 줄이는 쪽이라 맞습니다. 어긴 요구가 없습니다.
- 알아 둘 값: 다음 조각이 「늘어나기만 하는 번호」로 견주는 꼴을 옮겨 쓸 때, 화면이 보낸 번호는 늘 서버가 지금 값으로 줄여야 합니다. 그래야 경고를 숨기는 길이 생기지 않습니다. 줄이는 한 줄(`:382`)이 이 꼴의 열쇠입니다.
