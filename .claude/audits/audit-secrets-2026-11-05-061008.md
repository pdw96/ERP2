## 부적합 목록

### NC-7 · 열쇠 만드는 안내가 「조직 전체 열쇠」 갈림길을 막지 않고, 만든 뒤 범위를 확인하는 단계도 없다
- 위치: `docs/deploy.md:98-104`, ADR 0014 `:29`
- 증상: 안내는 조직 Settings → API keys → Create new 에서 **Project-scoped** 를 고르라고 한다. 멈추라는 조건은 「Project-scoped 가 보이지 않으면」 하나뿐이다. 경고하는 대안도 다른 화면(Account settings)의 **개인 열쇠**뿐이다.
  - 같은 화면에서 만들 수 있는 **조직 전체 열쇠**는 이름이 나오지 않는다.
  - 만든 뒤 그 열쇠가 프로젝트 하나로 좁혀졌는지 보는 단계가 없다(4 의 확인은 지우기가 되는지만 본다).
- 근거: 저자는 화면으로 따라 하고 코드는 거의 모른다(`Profile.md`). Project-scoped 가 기본으로 골라져 있지 않거나 보이지 않을 때를 생각해 보자. 안내가 「개인 열쇠만 안 된다」로 읽히므로, 조직 열쇠를 만들어도 안내를 어긴 줄 모른다.
  - 그 열쇠는 조직의 모든 프로젝트를 다룬다.
  - GitHub 비밀값으로 들어가면, 이 레포에 push 할 수 있는 누구나 꺼낼 수 있다(OB-1).
  - ADR 0014 가 받아들인 근거 「이 프로젝트 하나로 좁혔고」가 거짓이 된다.
  - 전제: Neon 의 그 화면은 조직 열쇠와 프로젝트 한정 열쇠를 함께 만든다. Neon 문서 「Manage API keys」의 기억에 기댄 것이라 저장소 밖이다 — U-12 와 함께 확인한다.
- 심각도: **높음** — 전제가 확인되지 않아 잃는 것이 큰 쪽으로 뒀다.
  - 전제: 조직에 다른 프로젝트가 있을 수 있고, 조직 열쇠가 프로젝트를 지울 수 있다.
  - 그렇다면 새는 순간 되돌릴 수 없는 삭제가 가능하다.
  - U-12 가 「조직에 이 프로젝트 하나뿐 · 만든 열쇠는 프로젝트 한정」으로 판정되면 **보통**으로 내린다. 그때도 Revoke 뒤 다시 만들 때 같은 갈림길이 남는다.
- 제안 (고치지 않음):
  - (a) 1 에 「**Organization**(조직 전체) 열쇠는 만들지 않는다 — 이 프로젝트 말고도 다 다룬다」를 개인 열쇠 경고와 나란히 적는다.
  - (b) 1 끝에 확인 줄을 하나 둔다 — 「API keys 목록에서 `github-preview-cleanup` 줄의 범위(Project)가 `cool-smoke-75501764` 인지 본다. 아니면 Revoke 하고 다시 만든다」.
  - (c) 선택: 작업 파일이 지우기 전에 열쇠로 `GET /projects`(조직 목록)를 불러 성공하면 멈추게 한다. 프로젝트 한정 열쇠는 목록을 못 볼 것으로 보지만, Neon API 의 동작이라 U-12 의 근거로 확인한다.

## 확인불가 항목

### U-12 · 실제로 만든 열쇠가 이 프로젝트 하나로 좁혀졌고, 그 열쇠로 무엇을 할 수 있는가
- 체크 항목: 9
- 위치: `docs/deploy.md:98-104`, ADR 0014 `:39-43` (「Neon 의 Editor 권한」 · 「가지를 만들고 지우고 되돌리며, 비밀번호를 새로 받아」)
- 판정하려면 셋이 있으면 된다.
  - (1) 저자의 답 — 열쇠를 만든 뒤 Neon 조직 Settings → API keys 목록에서 `github-preview-cleanup` 의 범위가 프로젝트 `cool-smoke-75501764` 라는 것. 열쇠 값은 옮기지 않는다.
  - (2) 저자의 답 — 그 Neon 조직에 다른 프로젝트가 있는지(있다 / 없다).
  - (3) Neon 문서로 확인한 프로젝트 한정 열쇠의 권한.
    - 프로젝트를 지울 수 있는지
    - 역할 비밀번호를 **바꾸지 않고 읽는 것**(`reveal_password` · `connection_uri`)이 되는지
    - 그 권한을 Neon 이 「Editor」라고 부르는지 — ADR 의 표기를 맞추기 위해서다
- 누가 줄 수 있는가: (1) · (2) 저자, (3) Neon 문서를 볼 수 있는 메인 세션
- 틀렸을 때 잃는 것: 높음 — NC-7 의 전제와 같다.

## 관찰

### OB-1 · ADR 0014 는 열쇠의 힘은 적었지만, 누가 열쇠를 꺼낼 수 있는지는 적지 않았다
- 위치: ADR 0014 `:39-43`, `yml:7-9,22`
- 무엇: `NEON_API_KEY` 는 이 레포의 **첫 GitHub 비밀값**이다(`ci.yml` · `health-check.yml` 은 비밀값을 쓰지 않는다). 레포 비밀값이라 두 길로 읽힌다.
  - 이 레포의 아무 가지에 push 된 작업 파일이면 읽을 수 있다.
  - `pull_request` 이벤트는 **PR 쪽의 작업 파일**(merge ref)을 돌린다. 그래서 같은 레포 가지의 PR 이 이 파일을 고치면, 닫을 때 고친 판이 비밀값과 함께 돈다.
  - 그래서 push 권한이 있는 누구나 — pdw96, 그리고 이 레포에 가지를 올리는 Claude 세션 — 꺼낼 수 있다.
  - Neon API 가 비밀번호를 바꾸지 않고 **읽는 것**을 허용한다면(U-12 (3)), 새도 데모가 깨지지 않아 드러나지 않는다. 그러면 ADR 의 「새었다고 생각되면 Revoke」가 기댈 신호가 없다.
- 왜 부적합이 아닌가: ADR 은 열쇠의 힘과 받아들이는 근거를 적었다. 꺼낼 수 있는 사람을 나열하라는 요구는 없다. push 권한자는 원래 무엇이든 돌릴 수 있다.
- 알아 둘 값: 공동 작업자를 더하거나 조각 「인사」에서 다시 볼 때, 줄이려면 아래처럼 바꾼다.
  - 비밀값을 GitHub **Environment** 에 두고, 배포 가지 규칙을 `main` 으로 건다.
  - 이벤트를 `pull_request_target: closed` 로 바꾼다. 그러면 `main` 의 작업 파일만 돈다. PR 코드를 받지 않으므로 안전하다.

### OB-2 · ADR 0004 · 0010 의 「접속 정보는 Vercel 에만」은 글자로는 맞지만, 이제 GitHub 에서 닿는 길이 하나 더 있다
- 위치: ADR 0004 `:34`, ADR 0010 `:25-26`, 대장 U-9
- 무엇: GitHub 의 열쇠로 역할 비밀번호를 받아 DB 에 들어갈 수 있다(ADR 0014 `:40-41` 이 스스로 적었다). 두 ADR 의 문장은 그 길을 가리키지 않는다.
- 왜 부적합이 아닌가: 접속 문자열 자체는 여전히 Vercel 에만 있다. 위험은 ADR 0014 가 받아들였다.
- 알아 둘 값: 두 줄 끝에 「→ ADR 0014」를 달 수 있다. 대장 U-9(닫힘)의 근거에도 같은 표시를 다는 것은 저자가 정한다(대장 「무엇이 기록이고 무엇이 살아 있나」).

### OB-3 · 지울 가지를 PR 이 아니라 가지 이름으로 고른다
- 위치: `yml:25,45-46`
- 무엇: 같은 head 가지로 PR 이 둘 열려 있으면(base 가 다를 때) 문제가 생긴다. 하나를 닫으면 다른 PR 이 쓰는 미리보기 DB 도 지워진다. 닫았다 다시 연 PR 도 DB 가 없다.
- 왜 부적합이 아닌가: 데모(`main`) 가지는 이름 조건과 기본 가지 조건 둘로 막힌다. 지워지는 것은 이 레포 가지의 미리보기 DB 뿐이다. 그 DB 는 가상 샘플이다.
- 알아 둘 값: 「미리보기가 갑자기 연결 안 됨」을 보면 같은 가지의 다른 PR 이 닫혔는지 본다.

## 안 본 것
- **커밋 안 된 변경의 전체 diff** — 받지 못했다. 호출자가 든 파일만 지금 상태로 봤다.
- **앱의 라우트 · 서버 액션** — 이번 변경에 없다. 다시 훑지 않았다(지난 회차는 전수).
- **`audit-ops`**
  - `docs/deploy.md:114` 는 「자동 작업이 실패하면 GitHub 가 메일을 보낸다」고 적었다. 그러나 GitHub 문서에 따르면 머지 충돌이 있는 PR 에는 `pull_request` 작업이 돌지 않는다. 그런 PR 을 닫으면 실행도 메일도 없이 가지가 남는다. 실패 알림이 무엇을 덮는지는 관측의 일이다.
  - 가지가 새는지를 알아챌 신호도 없다(OB-1).
- **`audit-quality`** — 작업 파일의 스크립트를 시험하거나 lint(actionlint) 하는 것, CI.
- **`audit-internal`** — `architecture.md` 줄이 문서 규칙과 맞는지.
