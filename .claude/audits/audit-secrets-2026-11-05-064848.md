## 부적합 목록

### NC-8 · fork 를 거르는 까닭에 「비밀값도 오지 않는다」고 적었는데, `pull_request_target` 에서는 fork PR 에도 비밀값이 온다
- 위치:
  - `.github/workflows/preview-db-cleanup.yml:19`
  - `docs/adr/0014-preview-db-branch-cleanup.md:34`
- 증상: 두 곳 모두 fork 를 거르는 까닭을 둘로 적었다 — 「미리보기 DB 가 없고, **비밀값도 오지 않는다**」. 둘째 까닭은 `pull_request` 때의 사실이다.
  - `pull_request_target` 은 base 쪽 문맥에서 돈다. 그래서 fork 에서 낸 PR 에도 레포 비밀값을 준다(GitHub 문서의 이벤트 설명).
  - 지금 fork 를 막는 것은 `yml:20` 의 `if` **한 줄뿐**이다.
- 근거: 지금 결과는 같다. `if` 가 fork 실행을 막고, PR 코드는 돌지 않는다. 걸리는 것은 다음에 고칠 사람이다.
  - 그 사람이 「fork 에는 어차피 비밀값이 없다」는 주석을 믿고 `if` 를 지우거나 느슨하게 할 수 있다.
  - 그러면 남이 fork 에 이 레포 가지와 같은 이름의 가지를 만들어 PR 을 열고 닫기만 해도, 이 레포 PR 의 `preview/<그 이름>` DB 가 지워진다.
  - 열쇠 자체는 그때도 새지 않는다. PR 코드를 돌리지 않기 때문이다.
- 심각도: **낮음** — 지금 결과는 같고, 글만 틀렸다. 같은 주석이 그대로 남은 채 `if` 가 빠지면 잃는 것은 가상 샘플 미리보기 DB 하나다. 다음 배포 때 다시 생긴다.
- 제안 (고치지 않음): 두 줄을 이렇게 바꾼다 — 「`pull_request_target` 은 fork PR 에도 비밀값을 준다. 이 조건이 fork 를 막는 유일한 장치라 지우지 않는다. 또 fork 에는 미리보기 DB 도 없다」.

### OB-4 · `pull_request_target` 으로 막힌 것은 「이 파일을 고쳐 꺼내는 길」 하나다. 열쇠를 꺼낼 수 있는 사람의 경계는 그대로 push 권한이다
- 위치:
  - ADR 0014 `:28-30` — 「PR 의 가지가 작업 파일을 고쳐 열쇠를 꺼내지 못하고」
  - ADR 0014 `:45` — 「열쇠를 꺼낼 수 있는 것은 … push 할 수 있는 사람」
  - `yml:7`
- 무엇: `NEON_API_KEY` 는 레포 비밀값이다. 그래서 push 권한이 있으면 어느 가지에서든 새 작업 파일을 더해 꺼낼 수 있다(예: `on: push`). 이 파일을 고칠 필요가 없다.
  - `:28-30` 은 이 파일에 대해서는 맞다.
  - 전제가 하나 있다. `pull_request_target` 이 base 가 `main` 이 아닌 PR 에서도 기본 가지의 작업 파일을 돌린다는 것이다. 이것은 GitHub 의 2025-12 변경을 기억한 것이고, 저장소 밖이다.
  - 다만 이 전제가 틀려도 경계는 바뀌지 않는다. 그 길을 쓸 수 있는 사람도 push 권한자뿐이기 때문이다.
- 왜 부적합이 아닌가: ADR `:45` 가 실제 경계(push 권한자 = 저자와 Claude 세션)를 바르게 적었고, 저자가 받아들였다.
- 알아 둘 값: `:28-30` 만 읽으면 「PR 쪽에서는 열쇠를 못 꺼낸다」로 오해하기 쉽다. 경계를 실제로 좁히는 것은 지난 OB-1 의 둘째 절반이다 — 비밀값을 Environment 로 옮기고 `main` 에만 열어 둔다. 대장 기록대로 조각 「인사」 또는 공동 작업자가 늘 때 다시 본다.
