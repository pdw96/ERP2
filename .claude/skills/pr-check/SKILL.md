# PR 점검

지금 가지가 기본 가지(`origin/main`)에 견주어 바꾼 것을 `CLAUDE.md` 의 작업 규칙에 대어 본다. **규칙의 원천은 `CLAUDE.md` 와 그것이
가리키는 ADR 이다** — 이 문서는 무엇을 어떻게 볼지만 든다. 둘이 어긋나면 `CLAUDE.md` 를 따르고, 어긋났다고 보고한다.

점검은 **보고만 한다.** 걸린 것을 스스로 고치지 않는다 — 무엇이 걸렸고 어떻게 고칠 수 있는지 보이고, 고칠지는 저자가 정한다.
(형식 · 린트처럼 업무에 영향이 없는 것은 고치겠다고 알리고 고쳐도 된다.)

## 준비

```bash
git fetch origin main
git diff --stat origin/main...HEAD
git diff --name-status origin/main...HEAD
```

커밋하지 않은 고침이 있으면 그것도 본다(`git status --short`). 바뀐 파일이 없으면 「점검할 것이 없다」고 알리고 끝낸다.

## 점검 일곱

해당하지 않는 항목은 「해당 없음」으로 적는다. 건너뛰지 않는다.

### 1. 착공 PR 인가, 구현 PR 인가

- 바뀐 파일에 새 `docs/slices/<조각>/requirements.md` · `design.md` 가 있으면 **착공 PR** 이다. 착공 PR 에는 결정 문서만 싣는다 —
  요구사항 · 설계 · ADR(`docs/adr/`) · `docs/master-plan.md`, 범위를 고쳤으면 `INTENT.md`. 그 밖의 파일(구현 코드 · 시험 · 샘플 ·
  `CLAUDE.md` · `Profile.md` · `docs/schema.md` · `docs/architecture.md`)이 섞였으면 걸린다(ADR 0027).
- **구현 PR** 이면 그 조각의 요구사항 · 설계가 `origin/main` 에 이미 있어야 한다. 없으면 「착공 PR 이 머지되기 전에 구현 코드를
  쌓지 않는다」에 걸린다. 구현이 설계 ⑥ 의 PR 나눔 가운데 어느 것인지도 적는다.

### 2. 범위 변경 한 줄

`docs/master-plan.md` 의 「모듈과 메뉴」 · 「만드는 순서」나 `INTENT.md` 가 바뀌었으면, 같은 PR 이 마스터플랜 「범위 변경」 표에
한 줄을 더했어야 한다 — 메뉴 이름 · 나눔만 바뀌어도 적는다. 「조각 나눔」의 상태 · 조각 폴더 칸만 바꾼 것은 적지 않는다(ADR 0024).

```bash
git diff origin/main...HEAD -- docs/master-plan.md INTENT.md
```

### 3. 샘플 이름

샘플 데이터(`src/db/sample.ts` 와 시험이 쓰는 이름)에 회사 · 사람 · 품목 이름을 더하거나 바꿨으면:

- 더하거나 바꾼 이름의 **목록**을 뽑는다. PR 본문에 그대로 실어 저자가 본다.
- 이름 자체가 실제 회사 · 실제 사람과 겹치지 않아야 한다. 「(가상)」 머리만으로는 채우지 않는다. 겹칠 만한 이름은 그렇다고 적는다 —
  확실하지 않으면 「확인 못 함」으로 적고 저자에게 넘긴다.
- 이 PR 이 건드리지 않은, 이미 있던 이름은 보지 않는다(소급하지 않는다, ADR 0024).

```bash
git diff origin/main...HEAD -- src/db/sample.ts
```

### 4. 재고 · 생산 계산의 시험

재고 · 생산의 셈을 바꾸는 고침(수불이 현재고에 반영되는 방식, 실사, BOM 의 필요량, 생산실적의 자재 차감 — `src/db/stock*.ts` ·
`src/db/boms.ts` · `src/lib/*stock*` · `src/lib/bom-input.ts` 와 그 마이그레이션 따위)이 있으면:

- 같은 PR 에 그 셈을 확인하는 시험이 있어야 한다. 시험 없이 머지하지 않는다.
- 시험이 바뀐 셈을 **실제로** 확인하는지 본다 — 파일만 있고 바뀐 규칙을 넣어 보지 않으면 걸린다.
- 앵커볼트(재고 계산 규칙 · 업무 용어 · 코드 체계)가 바뀌었으면, 저자에게 먼저 물은 자취(ADR · 설계의 저자 판정)가 있어야 한다.
  없으면 걸린다 — 고치지 말고 저자에게 묻는다.

### 5. 기록을 고치지 않았나

머지된 조각의 요구사항 · 설계, ADR, 감사 기록은 기본 가지에 있는 줄을 바꾸거나 지우지 않는다. 고치기 도구는 훅
(`.claude/hooks/protect-records.mjs`)이 막고, 셸 명령으로 고친 것은 일을 마칠 때 도는 마무리 검사
(`.claude/hooks/check-records-on-stop.mjs`)가 잡는다. 둘 다 Claude 의 세션 안에서만 돌므로 — 사람이 직접 고쳤거나 다른 도구가 고친 것까지 —
여기서 가지 전체를 다시 본다.

```bash
git diff --numstat origin/main...HEAD -- docs/adr docs/slices .claude/audits AGENTS.md
```

둘째 칸(지운 줄)이 0 이 아닌 파일이 걸린다. 부적합 대장(`docs/audit/nc-ledger*.md`)은 원 지적(「무엇」 칸과 첫 판정)과 회차 절이
기록이다 — 숫자로는 가를 수 없으니 고친 줄을 읽고, 지난 항목의 글자를 고쳤으면 걸린다. 상태 칸을 바꾸거나 닫힌 줄을 지나간 쪽으로
옮긴 것은 걸리지 않는다.

### 6. 감사 브리핑

`.claude/briefs/` 에 새 파일이 있으면, 그 감사 기록(`.claude/audits/`) · 대장의 등록과 **한 커밋**에 들어 있어야 한다(ADR 0024).

```bash
git log --name-status origin/main..HEAD -- .claude/briefs .claude/audits docs/audit
```

### 7. CI 가 보는 것을 미리

```bash
npm run format:check
npm run lint
npm run typecheck
npm test
python3 tools/doc-check/scripts/verify-docs.py --repo .
```

문서만 바꾼 PR 이면 끝의 문서 검사만 돌려도 된다. 떨어진 것은 무엇이 왜 떨어졌는지 적는다.

## 보고

`Profile.md` 대로 쓴다 — 업무 말로, 명령이나 코드가 아니라 결과(무엇이 걸렸고 어디에 남나)로.

1. **한 줄 결론** — 「올려도 된다」 / 「N 가지를 먼저 봐야 한다」.
2. **표** — 일곱 항목마다 통과 · 걸림 · 해당 없음 · 확인 못 함, 그리고 한 줄 근거.
3. **걸린 것마다** — 무엇이 어느 규칙에 걸렸나, 어떻게 고칠 수 있나. 업무에 영향이 있거나 절차에 걸린 것은 선택지를 보이고 저자가
   고른다.
4. **PR 본문에 실을 것** — 샘플 이름 목록(3), 범위 변경 줄(2)처럼 본문에 들어가야 하는 것을 그대로 붙일 수 있게 적는다.

「확인 못 함」을 「통과」로 적지 않는다. 돌리지 못한 검사는 못 돌렸다고 적는다.
