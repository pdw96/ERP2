# 조각 착공

조각마다 요구사항 · 설계를 한 PR(**착공 PR**)로 먼저 머지하고, 구현은 그 뒤 설계 ⑥ 의 나눔대로 낸다(`CLAUDE.md` 「작업 방식」, ADR 0027).
이 스킬은 착공 PR 을 여는 데까지다. **구현 코드는 쓰지 않는다** — 착공 PR 이 기본 가지에 머지되기 전에 구현을 쌓지 않는다(`CLAUDE.md` 「금지」).

규칙의 원천은 `CLAUDE.md` · `Profile.md` 와 그것이 가리키는 ADR 이다. 이 문서는 순서만 든다 — 어긋나면 `CLAUDE.md` 를 따르고 어긋났다고 알린다.

## 1. 어느 조각인가

```bash
git fetch origin main
```

- 인자로 조각 이름을 받았으면 그 조각이다. 없으면 `docs/master-plan.md` 「만드는 순서」에서 상태가 「예정」이고 **의존이 모두 「닫힘」인
  가장 앞 순서**의 조각이다.
- 상태가 「진행」인 조각이 남아 있으면 먼저 알린다 — 그 조각을 닫지 않고 새로 착공할지는 절차 결정이라 저자가 고른다(`Profile.md`).
  추천과 결과(무엇이 어디에 남나)를 함께 보인다.
- 가지는 `origin/main` 에서 새로 세운다. 다른 일이 섞인 가지에서 착공하지 않는다.

## 2. 넘어온 물음을 모은다

앞 조각 · ADR · 감사가 「<이 조각>의 착공에서 정한다」로 넘긴 것이 여러 문서에 흩어져 있다. 빠뜨리면 착공 뒤에 같은 물음이 감사로
되돌아온다. 이름으로 찾는다.

```bash
grep -rn "「<조각 이름>」" docs INTENT.md CLAUDE.md | grep -n "착공\|정한다\|넘긴\|기한"
```

읽을 것:

- `INTENT.md` — 이 조각이 의도의 무엇을 채우나, 「Not」에 걸리는 것은 없나.
- `docs/master-plan.md` — 이 조각의 목표 한 줄 · 의존, 「모듈과 메뉴」에서 이 조각이 짓는 메뉴, 「범위 변경」에서 이 조각을 가리키는 줄.
- `docs/adr/` — 이 조각을 「조각:」 줄이나 결과에 든 것 모두. 끝의 덧붙임 · 대체까지.
- 의존하는 조각들의 `requirements.md` 끝 「닫으며」의 「넘긴 것」과 `design.md` 끝의 날짜 항목.
- 바로 앞에 닫은 조각의 설계 끝 — 「다음 조각부터 이렇게 쓴다」 같은 약속(예: 조각 「재고 현황」 설계 끝 — 캡처는 세션 대화로, PR 본문에는 잰 값).
- `docs/audit/nc-ledger.md` — 기한이 이 조각(의 착공)인 열린 NC · U.
- `docs/schema.md` · `docs/architecture.md` — 지금 무엇이 있나.

모은 것은 목록으로 저자에게 보인다(3 의 물음과 함께).

## 3. 착공 인터뷰 — 저자가 정할 것을 묻는다

`Profile.md` 「결정을 가르는 법」대로 가른다. 애매하면 업무에 영향이 있는 결정으로 다뤄 묻는다.

| 무엇 | 누가 | 묻는 꼴 |
|---|---|---|
| 업무에 영향(장부 · 화면 · 재고에 무엇이 어떻게 남나) | 저자 | 업무 장면으로. 재고 · 생산은 **선택지 먼저, 추천은 뒤**. 구매 · 영업은 흐름을 짚으며. 회계 · 인사는 일반적인 ERP 의 흐름을 근거로 **추천 먼저** |
| 앵커볼트(재고 계산 규칙 · 업무 용어 · 코드 체계) | 저자 — 반드시 | 위와 같고, 정한 값은 ADR 에 든다 |
| 절차 · git · PR | 저자 | 추천안과 그 결과(무엇이 어디에 남나)를 먼저 |
| 업무에 영향이 없는 기술 | Claude 가 정하고 알림 | 한두 줄. 대안이 있던 것은 설계 ④ 와 ADR 에 |

- 묻는 것은 `AskUserQuestion` 으로, 한 번에 넷 이하로 나눠 묻는다. 물음마다 혼자 읽어도 알 수 있게 장면을 넣는다.
- 저자가 고른 것은 그 자리에서 「저자 판정(<날짜>, 추천대로 / 다르게)」으로 적어 둔다 — ADR 의 「결정」에 그대로 옮긴다.
- 샘플 데이터에 새 회사 · 사람 · 품목 이름이 들 것 같으면 그 이름의 목록을 여기서 보이고 저자가 본다. 실제 이름과 겹치지 않게 짓는다 —
  「(가상)」 머리만으로는 채우지 않는다(ADR 0024 의 3).

## 4. 문서를 쓴다

틀은 `tools/doc-check/templates/` 에 있다. 틀의 `##` 제목은 글자 그대로 두고(문서 검사가 본다), 틀 머리의 주석과 `<…>` 는 지운다.

**조각 폴더** — `docs/slices/<순서>-<이름>/`. 이름의 띄어쓰기는 붙인다(예: `3-재고수불`, `5-BOM`).

**`requirements.md`** — 틀의 다섯 제목(문제 · 핵심 사용자와 시나리오 · 성공 기준 · 하지 않을 일 · 제약).

- 첫 줄은 `# 조각 <순서> — <이름> (<YYYY-MM-DD> 착공)`.
- 문제는 데모에서 지금 보이는 것(메뉴가 「준비 중」 따위)과 뒤 조각이 기대는 것으로, 숫자가 있으면 숫자로.
- 시나리오는 데모 주소에서 어디를 누르면 무엇이 보이는지 처음부터 끝까지 한 흐름으로, 샘플 품목 · 코드를 넣어.
- 성공 기준은 데모에서 확인할 수 있는 동작이나 숫자로, 번호를 매긴다.
- 제약에는 적어도 — 스택 · 배포처(ADR 0001 · 0002) · 비용, 저자가 정한 것과 그 ADR(바꾸려면 먼저 묻는다), 샘플 이름 규칙, 계산을 바꾸면
  시험(`CLAUDE.md` 「금지」), 리뷰 한도(한 PR 에서 리뷰가 5회차를 넘기면 저자가 판정), 감사 회차.
- **감사 회차** — 언제 어느 감사자를 왜. 이 레포에 있는 감사자는 `.claude/agents/` 에 있는 것이다(지금은 `audit-internal`). 없는
  감사자(데이터 · 운영 · 비밀값)가 필요해 보이면 「필요하나 레포에 감사자가 없다」로 적고 저자에게 넘긴다. 대장에서 기한이 이 조각인
  줄의 담당도 적는다.

**`design.md`** — 틀의 여섯 제목(① 바뀌는 것 ~ ⑥ PR 나눔). 해당이 없으면 `없음 — <이유>`.

- ① 은 파일 · PR · 무엇의 표. 앵커볼트를 건드리면 그렇다고 적는다. 표 · 마이그레이션이 늘면 적는다.
- ④ 는 「정한 것」(ADR 번호)과 「열어 둔 것」(⑥ 의 어느 PR 이 그 PR 을 열기 전에 정하나).
- ⑤ 는 무엇으로 맞음을 보일지 — 재고 · 생산 계산이면 시험의 규칙(경계 · 거절 · 같은 때의 두 요청). 화면은 미리보기를 세션 대화로
  저자에게 캡처해 보이고, PR 본문에는 잰 값(표 폭 · 줄 수 · 시나리오의 수)을 싣는다.
- ⑥ 은 구현 PR 의 나눔 — 하나가 리뷰할 수 있는 크기로.

**ADR** — 대안이 있던 결정마다, 또는 한 착공의 결정을 묶어 하나. 번호는 `docs/adr/` 의 다음 번호.

```markdown
# ADR <번호> — <무엇을 정했나 한 줄>

- 날짜: <YYYY-MM-DD>
- 상태: 정함
- 조각: <짓는 조각>(짓는다) · <기대는 뒤 조각>(무엇에 쓴다)

## 맥락
## 대안
## 결정
<저자가 고른 것 — 저자 판정(<날짜>, 추천대로 / 다르게). Claude 가 정한 기술 결정은 그렇다고>
## 결과
<뒤 조각이 착공에서 정할 것은 「조각 「…」은 착공에서 …을 정한다」 꼴로 — 다음 착공이 2 의 grep 으로 찾는다>
```

**마스터플랜** — 「만드는 순서」에서 이 조각의 상태를 「진행」으로, 조각 폴더 칸을 `docs/slices/<순서>-<이름>/` 로. 이 둘만 바꿨으면
「범위 변경」에 적지 않는다. 「모듈과 메뉴」 · 「만드는 순서」의 다른 칸(메뉴 이름 · 나눔 · 목표 · 의존)이나 `INTENT.md` 를 고쳤으면
「범위 변경」에 한 줄(날짜 · 무엇을 · 왜 · 어느 조각에서)을 더한다(ADR 0024 의 1).

## 5. 검사

```bash
python3 tools/doc-check/scripts/verify-docs.py --repo .
git diff --name-only origin/main...HEAD
git status --short
```

- 문서 검사가 PASS 여야 한다. 떨어지면 무엇이 왜 떨어졌는지 보고 고친다.
- 바뀐 파일은 **결정 문서뿐**이어야 한다 — `docs/slices/<조각>/requirements.md` · `design.md`, `docs/adr/` 의 새 파일, `docs/master-plan.md`,
  범위를 고쳤으면 `INTENT.md`. 구현 코드 · 시험 · 샘플 · `CLAUDE.md` · `Profile.md` · `docs/schema.md` · `docs/architecture.md` 가 섞였으면 빼서
  착공이 머지된 뒤의 PR 로 넘긴다(ADR 0027 의 1).
- 이미 머지된 ADR · 조각 문서의 지난 줄을 고치지 않았는지 — 고쳐야 할 것은 그 문서 끝의 날짜 항목이나 새 ADR 로 잇는다(ADR 0024 의 2).
- 끝으로 `/pr-check` 를 돌려 일곱 항목을 본다.

## 6. 커밋 · 착공 PR

- 커밋 제목은 앞 착공의 꼴을 따른다 — `조각 「<이름>」 착공 — 요구사항 · 설계 · ADR <번호>(<한 줄>) · …, 마스터플랜 진행`.
- PR 은 초안으로 연다. 본문은 저자가 읽을 수 있게 업무 말로:
  1. **이 조각이 데모에 무엇을 더하나** — 시나리오를 짧게.
  2. **저자가 고른 것** — 물음 · 고른 답 · 그것이 장부 · 화면 · 재고에 남기는 것.
  3. **Claude 가 정한 기술 결정** — 무엇을 왜, 한두 줄씩.
  4. **넘어온 물음의 처리** — 2 에서 모은 것마다 어디서 정했나(이 착공 · 뒤 PR · 뒤 조각).
  5. **열어 둔 것** — 설계 ④ 그대로.
  6. 샘플 이름을 더하거나 바꿀 계획이면 그 목록.
- 머지는 저자가 한다. 머지되기 전에는 구현을 시작하지 않는다 — 저자가 「구현 시작」을 말하고 착공 PR 이 기본 가지에 있을 때 설계 ⑥ 의
  첫 PR 을 연다.
