# ADR 0006 — 설계도를 데모 안의 그림으로 본다

- 날짜: 2026-11-02
- 상태: 정함
- 조각: 기준정보

## 맥락

저자는 코드보다 화면으로 판단하고(`Profile.md`), 글로 쓴 설계만으로는 전체가 잘 보이지 않는다고 했다(2026-11-02). 데모 안
어딘가에서 전체 설계를 그림으로 보고 싶다고 요청했다. 채용 담당자에게도 「무엇을 어떻게 지었나」를 보이는 자리가 된다
(`INTENT.md` What — AI 로 지은 과정이 보인다).

## 대안

어디에 두나는 저자가 「앱 안 어딘가」로 맡겼고, 어떻게 그리나는 업무에 영향이 없는 기술 결정이라 Claude 가 정했다.

1. **Mermaid 글을 앱이 그린다** — 그림을 글(Mermaid)로 써 두고, 설계도 화면이 열릴 때 브라우저가 그린다. 글이라 PR 의 바뀐 줄로
   그림의 변화가 보이고, GitHub 도 같은 글을 그림으로 보인다. 그리는 도구는 그 화면에서만 내려받는다.
2. **손으로 그린 SVG** — 모양은 마음대로지만, 조각마다 고치기가 무겁고 PR 에서 무엇이 바뀌었는지 읽기 어렵다.
3. **그림 파일(PNG)** — 고칠 때마다 다른 도구로 다시 그려야 하고, 바뀐 것이 PR 에서 보이지 않는다.

## 결정

1 을 고른다 — 다만 스윔레인은 Mermaid 가 칸을 지키지 못해(칸을 건너는 화살표가 있으면 칸 안의 방향을 버린다), 칸 · 단계 ·
화살표를 데이터로 적고 앱의 작은 그리기 부품이 SVG 로 그린다. 데이터 모델의 상세 · 시스템 구성 · Overview 는 Mermaid 다. 화면은 데모의
메뉴 판 아래 「설계도」(주소 `/design`)이고, 그림은 셋이다.

- **업무 흐름** — 저자가 모양을 골랐다(2026-11-02, 미리보기 셋 가운데 「부서별 칸」). 부서(인사 · 영업 · 생산 · 품질 · 재고 ·
  구매 · 회계)마다 세로 칸을 나눈 스윔레인 한 장 — 주문부터 월 마감까지 한 줄기로, 시작 · 끝 · 작업 · 판단(예 / 아니오)을 모양으로
  가르고, 칸을 건너는 화살표가 부서 사이의 이관이다. 품질 칸은 저자가 영역을 더하며 넣었다(같은 날). 그 뒤의 Overview 는 부서 일곱과 그 사이에 오가는 것을 간추린 한 장이다.
  재고 · 생산 · 구매 · 영업의 단계는 Claude 의 초안을 저자가 고치고, 회계 · 인사는 일반적인 ERP 흐름의 추천안이다 — 각 조각의
  착공에서 다시 정한다.
- **데이터 모델** — 두 장이다(저자 판정, 2026-11-02 PR A 검토). ① 모듈별 전체 지도 — 모듈(왼쪽 메뉴 순서)마다 테이블 이름과
  그것을 만드는 조각을 카드로 늘어놓고, 모듈 사이의 주요 흐름을 화살표 줄로 보인다. 선이 많아 Mermaid 로는 상자가 흩어져,
  데이터를 적고 앱이 카드로 그린다. ② 이 조각의 테이블 — 칸까지 보이는 Mermaid ER 그림. 지금 짓는 조각의 테이블을 따로 표시한다.
- **시스템 구성** — 브라우저 · 앱(Vercel) · DB(Neon) · 자동 검사 · 정기 확인 · 매일 밤 되돌림.

그림의 글과 스윔레인 데이터는 한 파일(`src/content/diagrams.ts`)에 둔다. 테이블 · 부품 · 흐름을 바꾸는 PR 이 같은 PR 에서 그림도 고친다.

## 결과

- 저자와 채용 담당자가 데모에서 바로 전체 그림을 본다.
- 그림은 손으로 고치는 것이라 코드와 어긋날 수 있다 — 리뷰와 닫기 전 감사가 본다.
- 그리는 도구(Mermaid)는 설계도 화면에서만 내려받아 다른 화면을 무겁게 하지 않는다.
