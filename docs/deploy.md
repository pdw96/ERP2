# 배포와 되돌리기

**살아 있는 문서**다. 데모를 Vercel(앱)과 Neon(DB)에 올리고 되돌리는 법을 든다. 고른 까닭은 ADR 0002.

이 문서의 1 · 2 · 3 은 저자가 한 번만 한다 — Claude 의 작업 환경에서는 가입과 연결을 할 수 없다. 화면의 단추 이름이
여기와 다르면 비슷한 이름을 고르고, 그 이름을 Claude 에게 알려 주면 이 문서를 고친다.

## 1. Vercel 에 레포 잇기

1. <https://vercel.com/signup> 에서 **Continue with GitHub** 로 가입한다. 요금제는 **Hobby**(무료)를 고른다.
2. 대시보드에서 **Add New…** → **Project** 를 누른다.
3. **Import Git Repository** 목록에 `ERP2` 가 없으면 **Adjust GitHub App Permissions** 에서 `pdw96/ERP2` 를 허용한다.
4. `ERP2` 옆 **Import** → 설정은 그대로 두고(Framework 는 Next.js 로 저절로 잡힌다) **Deploy** 를 누른다.
5. 1 ~ 2분 뒤 데모 주소가 나온다(프로젝트 첫 화면의 **Production Deployment** → **Domains**). 이 주소가 채용 담당자에게
   줄 데모 주소다 — **<https://erp-2-eta.vercel.app>**.
6. **Settings** → **Deployment Protection** 에서 **Vercel Authentication** 을 끈다. 켜 두면 PR 미리보기 주소를 Vercel 에
   로그인한 사람만 볼 수 있어 Claude 가 머지 전에 화면을 찍어 보일 수 없다. 미리보기도 샘플 데이터만 쓰는 공개 데모와
   같은 내용이라 감출 것이 없다(저자가 정함, 2026-11-02).

이때부터 `main` 에 머지하면 데모가 저절로 바뀌고, PR 마다 Vercel 이 미리보기 주소를 PR 댓글로 단다.

## 2. Neon DB 를 만들어 잇기

1. Vercel 의 ERP2 프로젝트에서 **Storage** 탭 → **Create Database** → **Neon** 을 고른다.
2. **Region** 은 **Washington, D.C., USA (East)** 를 고른다 — Vercel 서버의 기본 위치와 같은 곳이라 화면과 DB 사이가 짧다.
3. **Auth** 는 끈다 — 로그인은 이 단계에서 만들지 않는다(조각 「인사」가 정한다). **Realtime** 도 끈 채로 둔다.
4. **Installation Plans** 는 **Free** 를 고르고 **Continue** 를 누른다.
5. **Create** 뒤 프로젝트에 잇는 화면에서 **Custom Prefix** 는 비워 둔다 — 값을 넣으면 환경변수 이름이 `DATABASE_URL`
   에서 바뀌어 앱이 접속 정보를 찾지 못한다. 이을 환경은 **Production** 과 **Preview** 를 둘 다 켠다. 미리보기 배포마다 DB 분기를 만드는 선택지는 **반드시 켠다** —
   PR 미리보기가 데모 DB 를 건드리지 않게 하는 장치다. 선택지가 보이지 않으면 여기서 멈추고 Claude 에게 알린다.
   켜졌는지는 첫 미리보기 배포 뒤 Neon 콘솔 **Branches** 에 `preview/<가지 이름>` 분기가 생긴 것으로 본다.
6. 다 만들면 Vercel 프로젝트의 환경변수에 `DATABASE_URL` 이 저절로 들어간다(**Settings** → **Environment Variables**
   에서 이름만 확인하면 된다).
7. **Deployments** 탭 → 맨 위 배포의 **⋯** → **Redeploy** 를 눌러 환경변수를 반영한다.

## 3. 매일 밤 되돌림의 비밀값 넣기

데모의 데이터는 매일 밤 한 번(한국 시간 새벽 4시대) 샘플 데이터로 돌아간다(ADR 0004). Vercel 이 그 시각에 데모의
되돌림 입구(`/api/cron/reset`)를 부르는데, 입구는 비밀값을 아는 요청만 받는다. 그 비밀값을 Vercel 에 한 번 넣는다.
넣기 전에는 되돌림이 돌지 않는다 — 입구가 모든 요청을 거절할 뿐 데이터는 그대로다.

1. 비밀값을 만든다 — 아무도 짐작할 수 없는 32자 이상의 영문 · 숫자. Mac 이면 **터미널** 앱을 열어 아래 한 줄을 붙여 넣고
   Enter 를 누른다. 나온 64자가 비밀값이다(어디에도 따로 적어 두지 않아도 된다 — Vercel 만 알면 된다).

   ```bash
   openssl rand -hex 32
   ```

2. Vercel 의 ERP2 프로젝트 → **Settings** → **Environment Variables** 에서 새 변수를 넣는다.
   - **Key**: `CRON_SECRET`
   - **Value**: 1 의 64자
   - **Environments**: **Production** 만 켠다(Preview · Development 는 끈다) — PR 미리보기의 DB 는 되돌리지 않는다.
   - **Sensitive** 를 켠다 — 넣은 뒤에는 화면에서도 값이 보이지 않는다.
3. **Save** 를 누르고, **Deployments** 탭 → 맨 위 Production 배포의 **⋯** → **Redeploy** 로 반영한다.
4. **Settings** → **Cron Jobs** 에 `/api/cron/reset` 한 줄이 있는지 본다. 옆의 **Run** 을 누르면 지금 한 번 되돌린다 — 데모에
   누가 넣은 데이터가 지금 사라진다.

비밀값을 바꾸고 싶으면 2 의 값만 새로 넣고 3 을 한다. Hobby 요금제의 예약 작업은 하루 한 번이고, 정한 시(時) 안의 어느 때에
돈다 — 돈은 들지 않는다.

## 4. 확인하기

| 무엇 | 어디서 | 맞으면 |
|---|---|---|
| 화면 | 데모 주소 | 왼쪽에 모듈 아홉(기준정보부터 시스템 관리까지), 가운데 자재 흐름도. 「기준정보 › 품목」에 샘플 품목 10개, 「기준정보 › 거래처」에 7개(해외 2 — 데이터가 있던 DB 는 첫 매일 밤 되돌림 뒤부터, 그 전에는 5개가 모두 KR), 「재고 › 재고 기준정보 › 창고」에 4개, 「시스템 관리 › 공통코드」에 묶음 4개(단위 4개 · 국가 5개) |
| DB | 데모 주소 뒤에 `/health` | 「연결됨」과 한국 시각, 「마지막 되돌림」 시각. 결과는 1분마다 새로 확인한다 |
| 버전 | 같은 화면의 「배포 버전」 | 지금 떠 있는 배포의 커밋 앞 일곱 자리 — Deployments 탭의 커밋과 같다 |
| 자동 배포 | PR 을 머지하고 몇 분 뒤 데모 주소 | 머지한 변경이 보인다 |
| 미리보기 | PR 의 Vercel 댓글 | 미리보기 주소가 있고, 그 주소의 `/health` 도 「연결됨」 |
| 비용 | Vercel **Settings** → **Billing**, Neon 콘솔 **Billing** | Hobby · Free |
| 마이그레이션 | 배포의 **Building** 기록(Deployments 탭 → 배포 → **Build Logs**) | `마이그레이션: 적용된 것 N개 — 이번에 M개 적용` 과 `샘플 데이터: …` 두 줄 |
| 매일 밤 되돌림 | 데모의 `/health` 의 「마지막 되돌림」 | 오늘 새벽 4시대(한국 시간). **Cron Jobs** → **View Logs** 의 `되돌림 완료: …` 줄은 1시간 뒤 사라져, 시각은 `/health` 로 본다 |

`/health` 가 「연결 안 됨」이면 화면의 안내 문구를 읽는다 — 「설정되지 않았습니다」는 2 의 6 · 7 을, 「닿지 못했습니다」는
Vercel 배포의 **Logs** 에서 아래 꼴의 줄을 찾는다. 로그에는 접속 정보가 남지 않는다.

| 로그 | 뜻 | 예 |
|---|---|---|
| `DB 연결 실패: <코드>` | DB 까지 닿지 못했다 — 네트워크 · 주소 · 인증서 | `ECONNREFUSED` · `ENOTFOUND` |
| `DB 질의 실패: <코드> <등급> <메시지>` | DB 가 받아 놓고 거절했다 — 메시지가 원인을 말한다 | 무료 계산 시간 소진, 비밀번호 틀림(`28P01`) |
| `처리 실패: <이름>` | DB 는 거절하지 않았다 — 프로그램의 버그거나 접속 정보가 없다. 되돌림 · 배포 빌드 · 저장 · 불러오기의 줄이다(아래 문단) — 상태 화면의 확인에서는 같은 오류가 `DB 질의 실패: <이름> <메시지>` 로 남는다 | `TypeError`, `DatabaseUnsetError`(2 의 6 · 7) |

앞에 말머리를 단 줄이 더 찍힌다 — 배포 빌드의 `DB 준비 실패: …`(마이그레이션 · 첫 샘플, 그 배포는 나가지 않는다), 되돌림의
`되돌림 실패: …`(데이터는 그대로다), 품목 화면의 `품목 등록 실패: …` · `품목 수정 실패: …`(저장되지 않았고 화면이 다시 저장하라고
알린다) · `품목 목록 불러오기 실패: …` 따위의 `… 불러오기 실패: …`(화면이 「불러오지 못했습니다」를 보인다). 이 줄들은 방문자의
데이터에 닿으므로 DB 의 메시지 대신 코드 · 등급과 스키마의 이름만
남긴다 — 예: `DB 준비 실패: DB 질의 실패: 23514 ERROR table=items constraint=items_name_length`. 코드의 뜻은 PostgreSQL 오류 코드
표(<https://www.postgresql.org/docs/current/errcodes-appendix.html>)에서 찾는다. 시트의 `… 시트 등록 실패: …` 는 시트 **전체**가
저장되지 않았다는 뜻이다 — 고친 행만 있던 시트도 「등록」으로 적힌다.

Hobby 요금제는 로그를 1시간만 보관한다. 지난 실패 가운데 아래 「알림」이 보는 셋(연결 · 배포 버전 · 매일 밤 되돌림)은 그
실행 기록에 남는다 — 저장 · 불러오기의 실패는 남지 않는다(조각 「포트폴리오 정리」에서 오류 추적 도구를 붙인다, 대장 NC-2).

## 5. 미리보기 DB 가지 지우기

PR 마다 Neon 에 미리보기 DB 가지(`preview/<가지 이름>`)가 하나 생긴다. 무료 요금제는 가지가 10개까지라, 머지한 PR 의 가지가
쌓이면 다음 PR 의 미리보기 배포가 「Resource provisioning failed」로 시작도 못 한다. Vercel 화면에서 이은 Neon 은 GitHub 가지를
지워도 DB 가지를 지우지 않는다. 그래서 PR 이 머지되거나 닫히면 GitHub 의 자동 작업(`.github/workflows/preview-db-cleanup.yml`)이
그 PR 의 DB 가지를 지운다(ADR 0014). 자동 작업이 Neon 에 요청하려면 열쇠(API 키)가 필요하다 — 처음 한 번 넣는다.

1. **열쇠를 만든다** — Neon 콘솔(<https://console.neon.tech>)에서 왼쪽 위의 조직 이름을 누르고 **Settings** → **API keys** →
   **Create new** 를 누른다.
   - **Project-scoped** 를 고르고 프로젝트 `cool-smoke-75501764` 를 고른다 — 이 열쇠는 이 프로젝트 하나만 다룬다.
   - **Organization**(조직 전체) 열쇠는 만들지 않는다 — 이 프로젝트 말고 조직의 모든 프로젝트를 다루고 지울 수도 있다.
   - 이름은 `github-preview-cleanup`.
   - 만들면 열쇠가 **한 번만** 보인다. 복사해 두고 2 에 바로 넣는다(다른 곳에 적어 두지 않는다).
   - **Project-scoped** 가 보이지 않으면 여기서 멈추고 Claude 에게 알린다. 개인 열쇠(**Account settings** → **API keys**)도
     조직 열쇠처럼 내 계정의 모든 프로젝트를 다루므로 쓰기 전에 함께 정한다.
   - **만든 뒤 확인한다** — 같은 **API keys** 목록에서 `github-preview-cleanup` 줄의 범위가 프로젝트 `cool-smoke-75501764` 인지
     본다. 아니면(조직 전체로 보이면) 그 줄의 **Revoke** 를 누르고 다시 만든다.
2. **열쇠를 GitHub 에 넣는다** — GitHub 의 ERP2 레포 → **Settings** → **Secrets and variables** → **Actions**.
   - **Secrets** 탭 → **New repository secret** — **Name** `NEON_API_KEY`, **Secret** 1 의 열쇠 → **Add secret**.
   - **Variables** 탭 → **New repository variable** — **Name** `NEON_PROJECT_ID`, **Value** `cool-smoke-75501764` →
     **Add variable**. 프로젝트 ID 는 비밀이 아니다.
3. **이미 쌓인 가지를 손으로 지운다** — 자동 작업은 앞으로 닫히는 PR 만 지운다. Neon 콘솔 → 프로젝트 → **Branches** 에서
   머지되거나 닫힌 PR 의 `preview/…` 가지를 **⋯** → **Delete** 로 지운다. `main`(데모 DB)과 열린 PR 의 가지는 남긴다.
4. **확인한다** — 다음 PR 을 머지한 뒤 GitHub 의 **Actions** 탭 → **미리보기 DB 가지 지우기** 실행에
   `preview/<가지 이름>(br-…)를 지웠다` 한 줄이 있고, Neon 의 **Branches** 에서 그 가지가 사라졌다.

자동 작업이 실패하면 GitHub 가 메일을 보낸다 — 열쇠가 없거나(2), 지워졌거나, Neon 이 거절한 때다. 그때는 실행 기록의 마지막
줄을 읽고, 3 처럼 손으로 지운다. 열쇠가 새었다고 생각되면 1 의 화면에서 **Revoke** 하고 1 · 2 를 다시 한다.

GitHub 의 가지는 레포 → **Settings** → **General** → **Automatically delete head branches** 를 켜 두면 머지할 때 저절로 지워진다
— DB 가지와 따로다.

## 알림

GitHub Actions 의 「데모 상태 확인」(`.github/workflows/health-check.yml`)이 하루 4번(한국 시간 3:17 · 9:17 · 15:17 · 21:17)
데모의 `/health` 를 열어 세 가지를 본다. 하나라도 아니면 그 실행이 실패하고, GitHub 가 메일을 보낸다.

1. 「연결됨」 글자 — DB 가 끊겼거나 데모가 안 뜨면 걸린다.
2. 화면의 「커밋」이 `main` 의 최신 커밋과 같은가 — 머지 뒤 빌드가 실패했거나, 되돌린 뒤 Undo Rollback 을 잊어 데모가
   옛 버전이면 걸린다. 머지 직후라 빌드 중일 수 있어 최대 10분 기다린 뒤 판정한다.
3. 「마지막 되돌림」이 30시간 안인가 — 매일 밤 되돌림이 멈추면 걸린다. 되돌림 자체는 실패해도 메일을 보내지 않고 기록이 1시간
   뒤 사라지므로, 샘플을 넣은 시각으로 본다(대장 NC-10). 데모를 볼 때만 본다 — **Run workflow** 에 주소를 넣으면 보지 않는다.

**되돌림이 멈췄을 때**(3 의 메일) — 메일이 「시각을 읽지 못했다」이면 맨 아래 줄부터, 아니면 위에서부터 본다.

- 비밀값 — **Settings** → **Environment Variables** 에 `CRON_SECRET` 이 Production 으로 있는가. 없거나 바꿨으면 3(비밀값 넣기)의
  2 · 3 을 한다. 비밀값이 틀린 요청은 로그를 남기지 않는다.
- 예약 — **Settings** → **Cron Jobs** 에 `/api/cron/reset` 이 켜져 있는가.
- DB 의 거절 — **Run** 을 누르고 바로 **Logs** 에서 `되돌림 실패: …` 줄을 본다(4 의 표로 읽는다).
- 앞 배포로 되돌린 동안 — 「되돌리기」의 마지막 문단.
- 상태 화면이 시각을 읽지 못함 — 되돌림은 돌았을 수 있다. `/health` 가 「마지막 되돌림 읽지 못함」이고, **Logs** 에
  `마지막 되돌림 조회 실패: …` 줄이 있다(4 의 표로 읽는다). 정기 확인은 90초 뒤 한 번 더 열어 본 뒤에야 이 메일을 보낸다(대장 NC-14).
  이때는 **Run** 을 누르지 않는다 — 방문자의 데이터만 지워지고 까닭은 그대로다.

위 넷은 고친 뒤 **Run** 을 한 번 누르고 `/health` 의 「마지막 되돌림」이 지금 시각인지 본다.

- 받는 사람은 예약 실행이면 이 파일의 예약을 마지막으로 바꿔 머지한 계정, 손으로 돌린 실행이면 돌린 계정이다. GitHub
  **Settings** → **Notifications** → **Actions** 에서 실패 알림이 켜져 있는지 본다.
- 메일이 실제로 오는지 보려면 **Run workflow** 의 주소 칸에 없는 주소(예: `https://erp-2-eta.vercel.app/nope`)를 넣고 돌린다.
  실행이 실패하고 메일이 와야 한다.
- 실패한 날의 화면 글자는 그 실행 기록에 남는다(GitHub 가 90일 보관). **Actions** 탭 → 「데모 상태 확인」에서 본다.
- 바로 확인하고 싶으면 같은 화면의 **Run workflow** 로 한 번 돌린다.
- GitHub 의 예약 실행은 붐비면 늦거나 한 차례를 건너뛰기도 한다 — 위 시각은 대략이고, 한 차례가 빠지면 확인 간격이 12시간을
  넘을 수 있다(2026-11-02 첫 차례가 빠지고 다음 차례가 45분 늦었다, 대장 NC-5).
- 메일이 없다고 정상이라는 뜻은 아니다 — 돌지 않은 차례는 메일도 기록도 남기지 않는다. 데모를 건네기 전에는 **Actions** 탭 →
  「데모 상태 확인」에서 마지막 예약 실행의 시각을 보거나, **Run workflow** 로 한 번 돌린다.
- 레포를 공개로 바꾸면 오래 활동이 없을 때 GitHub 가 예약 실행을 멈출 수 있다 — 조각 「포트폴리오 정리」에서 확인한다.

## 되돌리기

배포한 데모가 잘못됐으면 바로 앞 배포로 곧바로 되돌린다. 코드를 고치지 않아도 된다.

1. **Deployments** 탭에서 지금 데모로 나가 있는 배포 **바로 아래의** Production 배포를 찾는다 — Hobby 요금제는 바로 앞 운영
   배포로만 되돌릴 수 있다. 지금 배포의 메뉴에서는 단추가 꺼져 있다(「already in Production」).
2. 그 배포의 **⋯** → **Instant Rollback** 을 누르고 확인한다.
3. 데모의 `/health` 를 열어 「배포 버전」의 커밋이 되돌린 배포의 것인지 본다.
4. **되돌린 동안에는 새로 머지해도 데모가 바뀌지 않는다.** 고친 코드를 머지한 뒤 Deployments 탭 위쪽의 **Undo Rollback**
   (또는 최신 배포의 **⋯** → **Promote to Production**)을 눌러야 새 배포가 데모로 나간다. 누른 뒤 3 처럼 커밋을 본다.
   되돌린 동안에는 데모가 `main` 의 최신과 달라 정기 확인(「알림」)이 하루 4번 「옛 버전이다」 실패 메일을 보낸다 — 예상된
   메일이고, Undo Rollback 을 누르면 멈춘다.

두 단계 이상 앞으로 가야 하면 Instant Rollback 으로는 안 된다 — 잘못 들어온 PR 들을 되돌리는 PR 을 만들어 머지한다(Claude 에게
「PR #○ 를 되돌려 줘」라고 하면 된다).

DB 는 되돌리기로 돌아가지 않는다 — 배포만 이전 것으로 바뀌고, 테이블과 데이터는 그대로다. 그래서 마이그레이션은 앞 배포의
코드와도 함께 돌게 쓴다(더하기만, 이름 바꾸기 · 지우기는 두 PR 로 — `docs/schema.md`). 데이터가 망가졌으면 매일 밤 되돌림을
기다리거나, 3 의 **Run** 으로 지금 샘플로 되돌린다.

**DB 가 앞 배포보다 앞서 있으면 매일 밤 되돌림을 끈다**(대장 NC-11). 되돌린 동안의 매일 밤 되돌림은 **앞 배포의 샘플**로 테이블을
다시 채운다. 그 사이에 마이그레이션이 공통코드 묶음 같은 값을 더했으면, 되돌림이 그 값을 지우거나(새 코드가 빈 목록으로 돈다)
새 참조에 걸려 실패한다. 머지 뒤 빌드가 실패해 마이그레이션만 적용된 때도 같다.

1. 되돌린 배포와 지금 배포의 **Build Logs** 에서 `마이그레이션: 적용된 것 N개` 의 N 을 견준다. 되돌린 배포의 N 이 작으면 DB 가
   앞서 있다.
2. 앞서 있으면 **Settings** → **Cron Jobs** 에서 `/api/cron/reset` 을 끈다(**Disable**). 그동안 「알림」의 3 이 「되돌림이 멈췄다」
   메일을 보낼 수 있다 — 예상된 메일이다.
3. Undo Rollback(또는 고친 배포의 Promote) 뒤에 다시 켜고 **Run** 을 한 번 눌러, `/health` 의 「마지막 되돌림」이 지금 시각인지 본다.
