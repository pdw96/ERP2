# 데이터 모델

**살아 있는 문서**다. DB 의 테이블과 그 규칙을 든다. 테이블을 더하거나 바꾸는 구현 PR 이 이 문서도 고친다.

## 테이블

테이블을 더하는 PR 이 아래 표에 한 줄씩 적는다. 정의는 `src/db/schema.ts`, 그림은 설계도 화면의 「데이터 모델」.

| 테이블 | 화면의 이름 | 무엇 | 조각 |
|---|---|---|---|
| `items` | 품목 | 코드(`RM-0001` · `SF-0001` · `FG-0001`) · 품명 · 규격 · 유형 · 조달구분 · 단위 · 수입 · 출하검사 대상 · 계획 정보(리드타임 · 안전재고 · 최소 발주 · 생산량 · 배수) · 사용 여부 | 기준정보 |
| `warehouses` | 창고 | 코드(`WH-01`) · 창고명 · 사용 여부 | 기준정보 |
| `partners` | 거래처 | 코드(`BP-0001`) · 거래처명 · 매입처 · 매출처 · 사업자등록번호 · 사용 여부 | 기준정보 |
| `code_groups` | 공통코드 묶음(Major) | 코드(`UNIT`) · 이름 · 시스템 코드 여부 | 기준정보 |
| `codes` | 공통코드 값(Minor) | 묶음 · 코드(`EA`) · 이름 · 정렬 순서 · 사용 여부. 묶음 + 코드가 겹치지 않는다 | 기준정보 |

### DB 가 막는 것

화면 · 서버의 검사를 건너뛴 값도 DB 의 제약이 거절한다 — 제약 이름이 `<테이블>_<무엇>` 꼴이라 거절된 칸을 가를 수 있다.

- **코드의 꼴**(ADR 0003 · 0009) — 품목 `^(RM|SF|FG)-[0-9]{4,}$` 이고 머리가 유형과 같다, 창고 `^WH-[0-9]{2,}$`, 거래처
  `^BP-[0-9]{4,}$`, 공통코드 묶음 `^[A-Z][A-Z0-9_]{1,19}$`, 값 `^[A-Z0-9][A-Z0-9_]{0,19}$`. 코드는 테이블(값은 묶음) 안에서 겹치지 않는다.
- **공통코드 참조** — 품목의 유형 · 조달구분 · 단위는 공통코드에 있는 값만 받는다. 품목에는 늘 같은 묶음 칸(`item_type_group` =
  `ITEM_TYPE` · `procurement_group` = `PROC_TYPE` · `unit_group` = `UNIT`)이 있어, 묶음 + 코드로 `codes` 를 가리킨다. 품목이 쓰는
  값은 지울 수 없다.
- **길이 · 범위** — 이름의 글자 수(설계 ③), 리드타임 0 ~ 365, 수량 0 이상, 정렬 순서 0 ~ 999,
  거래처는 매입처 · 매출처 가운데 하나 이상, 사업자등록번호는 비우거나 `000-00-00000` 꼴.

DB 가 막지 않고 서버가 막는 것(조각 「기준정보」 PR C · D · E) — 수량의 소수 넷째 자리(DB 는 `numeric(12,3)` 이라 거절하지 않고 셋째 자리로 반올림한다) · 수량의 상한, 코드 · 품목 유형을 등록 뒤 바꾸지 않음, 「사용 안 함」 단위를
새 품목에 쓰지 않음, 시스템 코드 묶음을 바꾸지 않음, 테이블마다 등록 상한.

### 샘플 데이터와 되돌림

- 샘플 데이터는 `src/db/sample.ts` 한 곳에 있다 — 가상 반도체 후공정 회사. 실제 회사명 · 사람 이름을 쓰지 않는다.
- 배포 빌드가 마이그레이션 뒤 DB 가 비어 있으면(공통코드 묶음이 0 행) 샘플 데이터를 넣는다. 데이터가 있으면 손대지 않는다.
- 매일 밤 한 번 되돌림(`/api/cron/reset`, ADR 0004)이 `src/db/reset.ts` 의 테이블을 비우고 샘플로 다시 채운다 — 번호(`id`)도
  1 부터. 한 트랜잭션이라 중간에 실패하면 아무것도 바뀌지 않는다. **테이블을 더하는 조각은 되돌림의 목록에도 더한다** —
  스키마와 목록이 다르면 시험이 실패한다.
- 코드 번호는 같은 머리의 가장 큰 번호 + 1 이다(`src/db/numbering.ts`) — 되돌린 뒤에는 샘플의 다음 번호부터 붙는다.

## 이름 규칙

- 테이블 · 컬럼 이름은 영어 소문자와 밑줄(`snake_case`)로 쓰고, 테이블은 복수형으로 쓴다(예: `items`).
- 화면에 보이는 업무 용어(한국어)와 테이블 이름의 대응은 위 표의 「화면의 이름」이 든다.
- 기본 키는 `id`(자동 증가 정수)다. 품목코드 같은 업무 코드는 `id` 와 따로 둔다 — 코드의 꼴은 앵커볼트(업무 용어 · 코드
  체계, `CLAUDE.md`)라 그 테이블을 만드는 조각이 저자에게 물어 정한다.
- 모든 테이블에 `created_at` · `updated_at`(시간대가 있는 시각)을 둔다.

## 접속

- 접속 정보는 환경변수 `DATABASE_URL` 하나로만 받는다. 값은 레포에 두지 않는다 — 데모는 Vercel 환경변수, 레포에는
  이름만 든 `.env.example`.
- 접속 코드는 `src/db/client.ts` 한 곳에 둔다(Drizzle ORM · postgres 드라이버).
- 접속은 암호화하고 서버 인증서를 확인한다(`verify-full`) — URL 의 `sslmode` 에 기대지 않는다. 내 컴퓨터의 DB(`localhost` ·
  `127.0.0.1`)만 예외다.

## 마이그레이션

- 테이블은 Drizzle 의 TypeScript 스키마(`src/db/schema.ts`)로 쓰고, `npm run db:generate` 가 SQL 마이그레이션 파일을 `drizzle/`
  에 만든다. 파일은 레포에 올려 리뷰에서 바뀌는 SQL 이 보이게 한다. 만든 SQL 은 손으로 고치지 않는다.
- 배포 빌드가 배포 전에 마이그레이션을 적용한다(`package.json` 의 `build` → `scripts/migrate.ts`, ADR 0005) — PR 미리보기는
  미리보기 분기 DB 에, `main` 은 운영 DB 에. 적용이 실패하면 빌드가 실패해 그 배포는 나가지 않고 데모는 앞 배포에 남는다.
- 빌드 기록에 두 줄이 찍힌다 — `마이그레이션: 적용된 것 N개 — 이번에 M개 적용`, `샘플 데이터: …`. 실패하면 `DB 준비 실패: <코드> …`
  (코드 · 등급과 스키마의 이름만 — 접속 정보도, 행의 값이 실릴 수 있는 DB 의 메시지도 남지 않는다. `docs/deploy.md`).
- 직결 주소(`DATABASE_URL_UNPOOLED`)가 있으면 그것으로 적용하고, 두 빌드가 같은 DB 에 동시에 적용하지 않게 잠금을 건다. 연결 풀
  주소(호스트에 `-pooler`)뿐이면 잠금 없이 적용한다 — 풀에서는 잠금이 다른 접속에 남을 수 있다.
- 한 빌드가 적용하는 마이그레이션은 한 트랜잭션이다 — 하나라도 틀리면 그 빌드의 마이그레이션은 하나도 적용되지 않는다.
- **앞 배포의 코드와도 함께 돌게 쓴다**(ADR 0005) — 배포를 앞 배포로 되돌려도(Instant Rollback) DB 는 돌아가지 않는다.
  - 더하기만 한다 — 테이블 · 칸 · 제약을 더한다. 새 칸은 비워도 되거나 기본값이 있어야 앞 배포의 등록이 실패하지 않는다.
  - 이름 바꾸기 · 지우기는 두 PR 로 나눈다 — 첫 PR 은 새것을 더하고 코드를 옮긴다, 둘째 PR(첫 PR 이 데모에 나간 뒤)이 옛것을 지운다.
  - 제약을 좁히는 변경(새 검사 · 새 참조)은 이미 있는 행이 지키는지 먼저 본다 — 아니면 적용이 실패해 배포가 멈춘다.
  - 되돌릴 마이그레이션(down)은 만들지 않는다. 잘못된 마이그레이션은 그것을 고치는 새 마이그레이션으로 덮는다.
